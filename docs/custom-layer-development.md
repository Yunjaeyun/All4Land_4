# 사용자 지정 레이어 개발 정리

작성 기준: 2026-11-05 로컬 코드. 이 문서는 현석 담당 기능의 의도·목표·구현 방법·사용 흐름을 설명한다. 로컬 구현 상태를 기준으로 하며 원격 브랜치 병합이나 운영 배포 완료를 의미하지 않는다.

## 1. 개발 의도

영국 관광 숙박·외식 추천 지도에서 사용자가 관심 있는 장소와 여행 동선을 직접 표시하도록 한다. 기존 치안·인구·녹지·숙소 주제도와 개인의 관심 정보를 같은 지도에서 함께 확인하는 것이 목적이다.

처음에는 마커 중심으로 시작했지만, 장소 한 점만으로는 여행 경로와 관심 구역을 표현하기 어려워 선과 면 도형을 추가했다. 이후 여러 사용자가 이용하는 상황을 고려해 **사용자당 개인 레이어 하나에 여러 장소·도형을 넣고, 각 항목에 조회 조건을 부여하는 구조**로 정리했다.

## 2. 목표와 담당 범위

- 지도 화면을 유지하면서 메뉴와 편집 패널을 전환한다.
- 마커·선·다각형·사각형·원으로 관심 장소, 경로, 구역을 표현한다.
- 항목마다 이름·월·시간·사진·색상·표시 여부를 관리한다.
- 등록·조회·수정·삭제를 화면부터 서버 저장 API까지 연결한다.
- 공용 DB와 로그인 작업이 완료되기 전에도 메모리 저장소로 개발·확인할 수 있게 한다.
- 추후 개인 관심 항목과 행정구역을 비교하는 여행지 추천 기능에 활용할 수 있도록 공간 정보를 보관한다.

팀 전체의 숙소 검색·맛집 관리·치안 지표 산출은 이 문서의 담당 범위에 포함하지 않는다.

## 3. 설계가 바뀐 이유

| 구분 | 초기 접근 | 현재 방식 |
|---|---|---|
| 개인 지도 구성 | 여러 레이어를 생성·관리 | 사용자당 개인 레이어 하나 |
| 조건의 소속 | 레이어 단위로 묶는 방식 | 장소·도형 항목별 월·시간 |
| 표현 방법 | 마커 중심 | 마커와 네 종류의 선·면 도형 |
| 조회 방법 | 레이어 선택 중심 | 항목의 조건에 맞춰 지도 표시 |
| 저장 구조 | 다중 레이어 배열 | 하나의 객체 안에 `features` 배열 |

예를 들어 같은 개인 레이어 안에 ‘9월 18시 노을 명소’, ‘10월 14시 산책 구역’, ‘9월 19시 이동 경로’를 함께 등록할 수 있다. 월·시간 조회는 각각의 항목에 적용한다.

## 4. 사용자 이용 흐름

1. 상단 메뉴에서 나만의 장소 지도를 연다. 기존 지도는 유지되고 편집 패널이 표시된다.
2. 이름·월·시간을 입력하고 사진과 색상을 선택한다.
3. 지도에서 마커 또는 도형 하나를 그린다. 마커는 좌표를 직접 입력해 추가할 수도 있다.
4. 선·다각형은 **그리기 완료 버튼, 더블클릭 또는 Enter**로 완성한다. Esc는 진행 중인 그리기를 취소한다.
5. **저장하기**를 누르면 서버에 저장을 요청한다. 성공하면 등록을 완료하고, 실패하면 도형과 입력 내용을 유지한다. 미등록 도형은 저장하거나 삭제해야 다음 도형을 추가할 수 있다.
6. 필요한 만큼 항목을 추가한다. 목록에서 표시·숨김, 정보 수정, 삭제를 수행하고 지도에서 위치·형상을 편집한다.
7. 조건 조회 탭에서 월과 시간 범위를 지정해 일치하는 항목을 확인한다.
8. 기존 항목을 수정하거나 삭제한 뒤에는 **변경사항 저장**을 누른다. 저장본은 페이지를 열거나 새로고침할 때 자동으로 불러온다.
9. 페이지 진입 시 저장본을 불러온다. 다시 불러오기를 선택하면 확인 후 현재 편집 내용을 저장본으로 교체한다.

추가 탭에서는 월·시간 조회 필터를 적용하지 않으며 항목별 표시 여부를 따른다. 조건 조회는 시작·종료 시간을 포함하고, 종료가 시작보다 이르면 자정을 넘는 범위로 해석한다. 예를 들어 22:00~02:00은 밤 10시부터 다음 날 새벽 2시까지다.

## 5. 구현 방법

### 화면과 지도

Thymeleaf 화면 조각으로 메뉴·개인 레이어 패널을 구성하고 JavaScript로 표시 상태를 전환한다. 별도 페이지로 이동하며 지도를 다시 만드는 대신 기존 지도에서 작업한다.

그리기는 Google Maps의 Marker·Polyline·Polygon·Rectangle·Circle과 지도 클릭 이벤트를 사용한다. 항목의 도형과 정보는 `CustomLayerDraw`가 관리하고, 저장·복원은 `CustomLayerStorage`가 담당한다. 저장할 때 화면 도형의 최신 좌표를 읽어 이동·꼭짓점 편집 결과도 반영한다.

### API와 저장소 분리

```text
편집 패널 / 지도
    → draw.js: 도형과 항목 정보 관리
    → storage.js: 전체 항목을 저장 데이터로 변환
    → /api/custom-layers
    → 사용자·세션 식별 + 입력 검증
    → LayerRepository
        ├─ 기본: 세션별 서버 메모리
        └─ layer-db: PostgreSQL/PostGIS (브라우저별 익명 저장 또는 계정별 저장)
```

화면과 API가 사용하는 데이터 형식은 저장소에 관계없이 같다. DB 연결 시에는 저장소와 사용자 식별 방식을 전환하도록 구성했다.

| 요청 | 동작 |
|---|---|
| `GET /api/custom-layers` | 개인 레이어 전체 조회 |
| `GET /api/custom-layers?month=9&start=17:00&end=19:00` | 항목별 조건 조회 |
| `PUT /api/custom-layers` | 개인 레이어 전체 저장·교체 |

빈 레이어는 `{"features":[]}`다. 조건 조회 결과가 전체 저장본을 자동으로 덮어쓰지는 않는다.

### 데이터 구성

```text
사용자
 └─ 개인 레이어 1개
     ├─ 항목: 이름, 월, 시간, 사진, 표시 여부
     │   └─ 도형: 종류, 색상, 좌표, 필요 시 반지름
     └─ 항목 여러 개
```

DB 준비 구조는 `users → user_custom_layers → custom_layer_features`다. 개인 레이어 여부와 사용자별 유일 조건을 추가하고, 기존 `custom_markers` 및 기존 레이어 데이터는 보존한다.

| 화면 도형 | PostGIS 저장 형태 |
|---|---|
| 마커 | Point |
| 선 | LineString |
| 다각형·사각형 | Polygon |
| 원 | 중심 Point + 반지름(m) |

공간 좌표는 WGS84(SRID 4326)를 사용하며 DB 좌표 순서는 경도(X), 위도(Y)다. 원의 영역을 공간 분석에 사용할 때에는 중심점과 반지름으로 실제 범위를 계산해야 한다.

### 저장 안정성과 사용자 구분

- 저장 전 ID 중복, 이름·월·시간, 좌표·도형 유효성, 사진 형식·용량 등을 검사한다.
- 기본 저장은 브라우저 세션별로 구분한다. 같은 세션에서 새로고침 시 복원되며 서버 재시작·세션 만료 시 초기화된다.
- DB 모드는 미로그인 시 `user_id`를 NULL로 두고 브라우저 쿠키로 레이어를 찾는다. 로그인 정보가 있으면 인증된 로그인 이름을 `users.login_id`와 연결한다.
- DB 전체 저장은 트랜잭션으로 처리한다. 사용자 행을 잠근 뒤 개인 레이어의 항목만 교체하며 실패 시 롤백한다.
- 저장·복원 중 편집을 제한하고, 저장 실패 시 현재 화면 내용을 유지한다. 최초 불러오기가 실패하면 저장을 막는다.
- 사진은 현재 Data URL 방식이다. 별도 파일 저장소·업로드 API는 후속 작업이다.

현재 전체 교체 방식에서는 같은 사용자의 여러 탭 중 마지막 저장이 우선하며 항목의 내부 DB PK가 바뀔 수 있다. 외부에서 항목을 식별할 경우 개인 레이어와 `client_feature_id`를 함께 사용해야 한다.

## 6. 현재 완료 범위와 남은 작업

| 항목 | 상태 |
|---|---|
| 지도 유지 메뉴·패널 전환 | 구현 |
| 마커·선·다각형·사각형·원 그리기 | 구현 |
| 완료 버튼·더블클릭·Enter·취소 | 구현 |
| 항목별 등록·수정·삭제·표시 제어 | 구현 |
| 월·시간 조건 조회 | 구현 |
| 서버 메모리 저장·복원 API | 구현 |
| 사용자당 개인 레이어 하나 구조 | 구현 |
| PostGIS 저장소·사용자 연결 코드·확장 SQL | 준비 코드 작성 |
| 로그인 없는 DB 저장 | 구현 및 로컬 PostGIS 임시 스키마에서 검증 |
| 공용 DB 스키마 적용·공통 로그인 통합 | 후속 작업 |
| 행정구역별 교차 개수 집계·여행지 순위 | 구현, 기존 LSOA 경계와 borough 구분 재사용 |

기존 다중 레이어 배열과 현재 단일 객체 형식은 호환되지 않는다. 기존 DB 데이터가 있다면 별도 변환이 필요하며 자동 삭제하거나 새 구조로 옮기지 않는다.

## 7. 검증 범위

테스트 코드는 다음 동작을 확인하도록 구성했다. 이 문서 작성 과정에서 테스트를 새로 실행하지는 않았다.

- JavaScript: 그리기 완료·취소, 미등록 도형 제한, 항목별 필터, 사진·수정·삭제, 저장·복원 및 실패 처리.
- 서버 통합: 세션 간 데이터 분리, 전체 저장·초기화, 입력 검증, 자정 통과 조회, 구형 데이터 형식 거부.
- DB 준비: 도형 변환, 잘못된 도형 거부, 로그인 사용자 식별 및 개발 설정 제한.
- 별도 PostGIS 테스트: 사용자별 저장 분리, 개인 레이어 유지, 교체 저장과 실패 롤백. 테스트용 임시 스키마를 사용한다.

이 검증 범위가 운영 DB 연결이나 최신 화면의 실제 브라우저 점검 완료를 뜻하지는 않는다.

## 8. 향후 확장 방향

개인 항목을 기존 행정구역과 비교해 여행 관심 지역을 찾는 기능을 추가했다. **점뿐 아니라 선·면·원이 행정구역에 걸치는 경우도 포함하고, 한 항목은 한 행정구에서 한 번만 센다.** 여러 구역에 걸치면 각 구역에 한 번씩 포함한다.

기존 지도와 동일한 LSOA 경계로 교차를 판정하고 기존 borough 속성으로 묶는다. 조회 조건에 맞는 표시 항목을 대상으로 항목 수 또는 사건률 기준을 선택해 정렬한다. 임의의 가중 점수는 사용하지 않는다. 관심 항목 수는 사용자의 관심도이며 안전도를 직접 의미하지 않는다. 상세 기준과 API는 [개인 관심 여행지 순위](custom-layer-ranking.md)를 참고한다.
